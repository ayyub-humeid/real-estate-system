# Real Estate Implementation Instructions

This repository contains a staged real-estate implementation plan.

Before executing any task under `real-estate-planning/`, first read:

```text
real-estate-planning/README.md
```

Treat that file as the master implementation contract.

Do not implement multiple phases at once unless the developer explicitly asks you to do so.

If this repository already has an `AGENTS.md`, merge these instructions into it instead of overwriting existing repository-specific instructions.

## Phase Delivery Guardrails

- Audit every new Filament resource and relation manager for its list, view, create, edit, delete, and workflow actions before declaring a phase complete. Explicitly document actions intentionally excluded by business-history rules.
- A policy ability must receive the arguments its policy method requires; header actions without a record must use a class-level ability or an explicit contextual model.
- Shield generates permissions for top-level resources only. Add relation-manager and workflow permissions to the custom-permissions UI, seed them, and verify role assignment in the running application.
- Every child record created from a relation manager must explicitly set `company_id` from the parent record using `mutateFormDataUsing` on the `CreateAction` AND `mutateFormDataBeforeCreate` on the relation manager class. The `HasCompany` trait intentionally skips auto-injection for super admins, so relation managers must never rely on the trait alone. Use explicit `$data['company_id'] = $this->getOwnerRecord()->company_id;` assignment — never `$data += [...]`.
- Do not use raw update/delete actions for ownership, legal, payment, or other historical records. Provide an explicit corrective/replacement workflow instead.
- After adding a new Filament/Livewire component, rebuild autoload metadata when needed and clear Laravel/Filament caches before manual verification.
- Verify current-phase workflows and authorization on both MySQL and PostgreSQL test databases before completion.

## Filament Shield Permission Naming Convention (MANDATORY)

This project uses **Filament Shield** with **Spatie Permission**. There are **two distinct permission naming conventions** depending on the permission category. Using the wrong convention causes resources to silently disappear from the dashboard even when the role has "all permissions" assigned. **Every policy must use the exact permission string that exists in the database.**

### Convention 1 — Shield-Generated Permissions (Top-Level Filament Resources)

Shield auto-generates permissions for every class that extends `Filament\Resources\Resource`. For multi-word model names, Shield converts the model name from `PascalCase` into a `::` delimited lowercase format.

**Formula:**

```
{action}_{first_word}::{remaining_words}
```

**Examples from this project:**

| Model Class           | Shield Permission Pattern           |
| --------------------- | ----------------------------------- |
| `Property`            | `view_property` (single word — no `::`) |
| `Unit`                | `view_unit` (single word — no `::`)     |
| `PropertyAcquisition` | `view_property::acquisition`        |
| `MaintenanceRequest`  | `view_maintenance::request`         |
| `CompanySetting`      | `view_company::setting`             |
| `UnitFeature`         | `view_unit::feature`                |
| `RentalRequest`       | `view_rental::request`              |

**Standard Shield actions (all must be present in the Policy):**

```
view_any, view, create, update, delete, delete_any,
force_delete, force_delete_any, restore, restore_any,
replicate, reorder
```

**Policy must use `HandlesAuthorization` trait.**

### Convention 2 — Custom Permissions (Relation Managers, Workflow Actions, Non-Resource Models)

Models that are **NOT** top-level Filament resources (e.g., relation manager children, workflow-only models) use **snake_case with underscores only** — no `::` separator.

These permissions are NOT auto-generated by Shield. They must be:
1. Manually created in the database (via seeder or Shield's custom permissions UI)
2. Manually assigned to roles

**Formula:**

```
{action}_{snake_case_model_name}
```

**Existing custom permissions in this project:**

### Decision Matrix: Which Convention To Use

```
Is the model a top-level Filament Resource (has its own ResourceClass extends Resource)?
  ├── YES → Convention 1: Shield-generated with :: separator
  │         Policy checks: action_{word1}::{word2}
  │         Permissions are auto-generated by `shield:generate`
  │
  └── NO  → Convention 2: Custom with _ separator
            Policy checks: action_{snake_case_model}
            Permissions must be seeded manually or added via Shield custom permissions UI
```

### Policy Template for Top-Level Resources (Convention 1)

```php
use Illuminate\Auth\Access\HandlesAuthorization;

class ExampleModelPolicy
{
    use HandlesAuthorization;

    public function viewAny(User $user): bool
    {
        return $user->can('view_any_example::model');
    }
    // ... all 12 standard abilities with :: separator
}
```

### Policy Template for Non-Resource Models (Convention 2)

```php
use App\Policies\Concerns\CompanyOwnedPolicy;

class ExampleChildPolicy
{
    use CompanyOwnedPolicy;

    public function viewAny(User $u): bool
    {
        return $this->canForResource($u, 'view_any_example_child');
    }
    public function view(User $u, ExampleChild $r): bool
    {
        return $this->canForRecord($u, 'view_example_child', $r);
    }
    // ... with _ separator, using CompanyOwnedPolicy helpers
}
```

### Verification Checklist (Run Before Declaring Any Phase Complete)

1. Run `shield:generate` for any new top-level resources.
2. Confirm Shield-generated permission names in the `permissions` DB table match the policy strings exactly.
3. For custom permissions: seed or add via Shield custom permissions UI, then assign to roles.
4. Log in as the target role and verify the resource/action appears correctly in the dashboard.
5. Log in as a role WITHOUT the permission and verify the resource/action is correctly hidden.
6. Clear caches: `php artisan optimize:clear && php artisan filament:cache-components`
